# YZBot 三人开发分工与逐步实施计划

## 1. 文档目的

本文用于指导三名团队成员循序渐进地完成“大模型技术创新赛”项目。所有任务按照前后依赖关系排列，原则是：

1. 先保证现有系统稳定运行；
2. 再确定模块接口，避免三个人各写一套数据格式；
3. 然后并行开发大模型、视觉、导航三条主线；
4. 基础能力稳定后再开发机械臂自动抓放；
5. 最后通过任务状态机将所有模块串成完整闭环；
6. 完成可视化、动态避障、五分钟压力测试和参赛材料。

在前一步没有达到验收标准前，不应盲目进入下一步。

## 3. 共同遵守的代码边界

为避免多人同时修改同一文件，采用以下规则：

| 文件或模块               | 默认负责人 | 其他人如何修改                     |
| ------------------- | ----- | --------------------------- |
| `bot_navigation/**` | A     | 先与 A 说明需求，通过独立分支提交          |
| 底盘 Xacro            | A     | B 可评审，但不直接同时修改              |
| 机械臂 Xacro、MoveIt 配置 | B     | A 负责集成评审                    |
| `tools_demo/**`     | C     | A、B 通过接口提出需求                |
| 组合模型入口 Xacro        | A     | B 提交修改建议，由 A 合并             |
| 比赛消息定义              | C     | 三人共同评审，接口冻结后才能修改            |
| 任务状态机               | A     | B、C 分别实现被调用的 action/service |
| 项目总文档               | C     | A、B 检查技术准确性                 |

任何需要修改他人负责文件的任务，都应先创建 issue 或在每日会议中确认。

## 4. 推荐新增的软件包

为了减少模块耦合，建议逐步增加以下 ROS 2 package：

```text
competition_interfaces/     # 比赛消息、服务和 Action
task_parser/                # 出题程序接入及大模型任务解析
cargo_perception/           # 红蓝货物识别和三维定位
manipulation_executor/      # MoveIt 抓取与放置
task_manager/               # 比赛任务状态机
competition_dashboard/      # 比赛可视化面板
competition_bringup/        # 全系统统一启动
```

不要把所有新功能继续堆进 `tools_demo` 或单个 Python 文件中。

## 6. 逐步实施计划

### 6.1 步骤 0：建立团队协作基础

建议时间：第 1 天上午。

负责人：成员 A。

成员 A：

1. 为主项目建立有效 Git 仓库；
2. 创建 `main` 或 `master` 稳定分支；
3. 创建 `develop` 集成分支；
4. 添加 `.gitignore`，排除 `build/`、`install/`、`log/` 和 `__pycache__/`；
5. 为三名成员建立各自开发分支；
6. 建立 issue/任务清单；
7. 将当前能运行的版本打上 `baseline-v1` 标签。

成员 B：

1. 检查 MoveIt、Gazebo、相机和抓取相关依赖；
2. 记录本机 ROS 2、MoveIt 和 Gazebo 版本；
3. 确认机械臂模型可以通过 Xacro 展开。

成员 C：

1. 检查 llama.cpp、模型文件和 Python 依赖；
2. 整理比赛规则、评分项和官方接口要求；
3. 建立 `docs/` 目录并维护团队文档。

本步骤产物：

- 可用的 Git 仓库；
- 明确的分支规则；
- 三人一致的环境清单；
- 项目基线标签；
- 统一任务看板。

验收标准：

- 三个人都能拉取代码、创建分支并提交；
- 主分支不包含构建产物；
- 当前代码有可恢复的版本基线。

在此步骤完成前，不开始大规模修改代码。

### 6.2 步骤 1：三人共同跑通现有系统

建议时间：第 1 天下午至第 2 天。

负责人：成员 A；三人共同参与。

按照以下顺序启动：

```bash
cd ~/dev_ws
colcon build --symlink-install
source install/setup.bash

ros2 launch mybot gazebo_world.launch.py
ros2 launch mybot my_moveit_rviz.launch.py
ros2 launch bot_navigation nav_bringup_gazebo.launch.py
```

成员 A 负责检查：

- Gazebo 是否完整加载；
- `/scan`、`/odom`、`/cmd_vel` 是否存在；
- `odom → base_footprint` TF 是否稳定；
- 设置 `2D Pose Estimate` 后是否出现 `map → odom`；
- Nav2 是否可以发送一个简单目标。

成员 B 负责检查：

- `/joint_states` 是否正常；
- `arm_controller` 和 `gripper_controller` 是否为 active；
- MoveIt 是否能规划和执行一个简单姿态；
- `/ATTACHLINK`、`/DETACHLINK` 服务是否存在；
- 手动吸附一个方块是否成功。

成员 C 负责检查：

- llama-server 是否能启动；
- `ros2 run tools_demo chat_ros` 是否能连接模型；
- `/llama_command` 是否有消息；
- 记录全部启动命令、报错和截图。

本步骤产物：

- 《基线运行记录》；
- 一份已知问题清单；
- 每个模块的启动截图；
- 当前 ROS 节点、话题、服务和 Action 清单。

验收标准：

- 三个人都能独立启动系统；
- 至少完成一次底盘手动移动；
- 至少完成一次机械臂轨迹执行；
- 至少完成一次手动 Attach/Detach；
- 至少完成一次大模型回复发布。

### 6.3 步骤 2：修复基础模型和控制问题

负责人：A、B；C 负责复测记录。

- 可重复的基础启动流程；
- 修正后的控制脚本；

- Xacro 和 URDF 检查全部通过；
- MoveIt 目标不会超出 Gazebo 控制范围；
- 夹爪轨迹不会超出 URDF 上限；

- `colcon build` 成功；
- 基础测试无新增失败。

该步骤不通过，后续导航和抓取结果都不可信。

### 6.4 步骤 3：设计并冻结模块接口

建议时间：第 5 天。

负责人：成员 C 编写接口，A、B 共同评审。

三人先在纸面或文档中确认以下数据：

1. 出题程序提供什么内容；
2. 大模型输出什么字段；
3. 视觉模块输出什么坐标系的位姿；
4. 导航模块需要什么目标；
5. 抓取模块需要什么参数；
6. 状态机如何判断成功或失败；
7. 可视化界面订阅哪些数据。

建议首先定义：

#### TaskPlan

```text
task_id
original_text
items[]
  sequence
  color
  target_zone
red_count
blue_count
```

#### CargoDetection

```text
object_id
color
confidence
pose
frame_id
timestamp
```

#### TaskProgress

```text
task_id
current_sequence
total_items
completed_items
work_state
gripper_state
elapsed_time
error_code
message
```

#### PickCargo Action

```text
Goal:
  object_id
  object_pose
  color

Result:
  success
  attached
  error_code
  message
```

#### PlaceCargo Action

```text
Goal:
  target_zone
  place_pose

Result:
  success
  detached
  error_code
  message
```

本步骤产物：

- `competition_interfaces` package；
- 消息、服务和 Action 定义；
- 坐标系约定；
- 错误码表；
- 状态枚举表；
- 接口说明文档。

验收标准：

- A 能根据接口编写状态机，不需要读取 B、C 的内部变量；
- B 能仅根据 Action Goal 执行抓放；
- C 能仅根据话题绘制界面；
- 三个人签字或明确确认接口；
- 接口冻结后，破坏兼容性的改动必须三人共同同意。

### 6.5 步骤 4：成员 C 开发大模型任务解析

建议时间：第 2 周前半段。

负责人：成员 C。

该步骤与步骤 5、步骤 6 并行进行。

依次完成：

1. 编写模拟出题程序，能够发布多种随机题目；
2. 收集至少 30 条不同表达方式的测试题目；
3. 设计固定 system prompt；
4. 要求模型只输出 JSON，不输出解释性文字；
5. 使用 JSON Schema 校验输出；
6. 校验颜色只能为 `red/blue`；
7. 校验区域只能为 `A/B/C`；
8. 校验数量和顺序一致；
9. 解析失败时自动重试一次；
10. 再次失败时发布明确错误状态；
11. 将结果转换成 `TaskPlan`；
12. 发布原始题目和结构化任务；
13. 增加单元测试。

禁止做法：

- 不允许直接执行大模型生成的 shell 命令；
- 不允许把未经校验的模型回复发送给机器人；
- 不允许依赖模型自由发挥 ROS 话题名称；
- 不允许解析失败后默认执行上一次任务。

本步骤产物：

- `task_parser` package；
- 模拟出题节点；
- 结构化提示词；
- JSON Schema；
- 题目测试集；
- TaskPlan 发布节点。

验收标准：

- 30 条测试题目全部能产生合法 JSON；
- 数量、颜色、顺序和放置区解析正确率达到 100%；
- 非法题目不会触发机器人动作；
- llama-server 不可用时能快速报错，不会永久阻塞；
- 单次解析时间有日志记录。

### 6.6 步骤 5：成员 B 开发红蓝货物视觉识别

负责人：成员 B。

该步骤与步骤 4、步骤 6 并行进行。

7. 由相机内参计算三维位置；
8. 使用 TF2 转换到 `base_link`；
9. 再转换到 `map`，供任务调度和导航使用；
10. 发布 `CargoDetection`；

12. 增加目标丢失、深度无效和遮挡处理；

本步骤产物：

- `cargo_perception` package；
- 红蓝颜色识别节点；
- RGB-D 三维定位节点；
- TF2 坐标转换；

验收标准：

- 仿真中静态目标连续 10 次识别稳定；

### 6.7 步骤 6：成员 A 完成比赛导航能力

## 9. Git 和代码评审规则


合并要求：

- 修改消息接口必须由三个人共同确认；
- 修改机器人模型必须由 A、B 互相评审；
- 修改状态字段必须由 A、C 互相评审；
- 发现回归后优先修复，不带着已知严重问题继续叠加功能。

## 10. 每个任务的完成定义

一个任务只有同时满足以下条件才算完成：

- 代码已经提交；
- 能在新终端中按照文档运行；
- 有成功和失败两种测试；
- 没有无限等待；
- 有超时和明确错误信息；
- 输出数据符合冻结接口；
- 不依赖开发者手动修改源码参数；
- 关键参数能够通过 ROS 参数或 launch 参数配置；
- 文档已经更新；
- 另一名成员能够复现。

“在我的电脑上运行过一次”不算完成。

## 11. 当前阶段不要提前做的事情

在完整闭环稳定前，暂时不要投入大量时间做以下工作：

- 不要频繁更换大模型；
- 不要先做复杂语音识别；
- 不要让大模型直接生成和执行机器人底层动作；
- 不要先制作非常复杂的月面材质和场景；
- 不要在静态导航未稳定时直接挑战动态障碍；
- 不要在单货物抓取未稳定时直接测试五货物；
- 不要同时维护两套不同消息接口；
- 不要只优化 RViz 效果而忽略比赛状态面板；
- 不要在比赛前最后几天重写核心架构。

## 13. 最终目标

三人最终不是分别展示“大模型能聊天”“机器人能导航”“机械臂能动”，而是共同交付一个完整系统：

```text
随机题目输入
→ 大模型正确解析
→ 视觉找到正确货物
→ 机器人按顺序导航
→ 机械臂抓取
→ 搬运到指定区域
→ 机械臂放置
→ 面板和播报全程更新
→ 5 分钟内完成任务
```

三人的模块必须通过冻结接口协作，所有开发都围绕比赛评分和完整任务闭环进行。
