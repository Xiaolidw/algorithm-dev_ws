# 8.31 路径规划、动态避障与 B 区停滞优化记录

> 本文件在优化过程中同步维护。内容来自实际运行日志、Gazebo 真值、当前 `dev_ws` 代码和参考工程对比；参考参数不直接照搬。

## 一、问题结论总览

### 1. B 区附近长时间停留

- 原目标：`(-1.0, -3.0, 90°)`。
- 多轮真值：差速底盘稳定停在约 `(-1.283, -2.991)`，剩余位置误差约 `0.28～0.30 m`。
- 根因：底盘已朝北，继续逼近原目标主要需要横向移动，差速结构无法直接完成；控制器会在安全边界旁反复旋转、恢复或等待。
- 已采用的几何修复：目标改为实测可达的 `(-1.28, -2.99, 90°)`；该位置直接放置的动态 IK 残差为 `1.3 mm`，物块可完整落入 B 区。
- 接管门限：由临时放宽的 `0.32 m` 收紧到 `0.22 m`，避免用大容差掩盖目标不合理。
- 状态：代码/配置已修改，尚需完成一轮真实 B 区搬运验证。

### 2. 图二撞墙与避障失效

- 原 Collision Monitor 订阅 `/scan_costmap`。
- `/scan_costmap` 为规划专用扫描：会过滤预测动态障碍附近的部分回波，并曾把全部小于 `0.42 m` 的有限回波置为无穷远。
- 直接后果：车辆最接近墙、石块或物块时，末级防撞反而可能看不见该实体。
- 已采用的结构修复：新增 `/scan_safety`，仅剔除机器人自身非对称轮廓内部回波，墙体、石块、货物方块和移动障碍全部保留；Collision Monitor 独立订阅 `/scan_safety`。
- 已有运行态证据：`/scan_safety` 发布约 `18.4～19.1 Hz`，Collision Monitor 是其订阅者。
- 新发现的物理盲区：Gazebo 激光原始 `range_min=0.50 m`，即使安全扫描不再删点，传感器本身仍不会生成最后 0.5 m 内的有效墙体回波。已把仿真激光最小量程改为 `0.10 m`；2026-08-31 运行态 `/scan` 已确认 `range_min=0.1000000015`。

### 3. 放置后下一任务立即 ABORTED

- 放置后方块中心与底盘中心约 `0.45～0.47 m`。
- 旧逻辑以 `0.42 m` 简化物理净空为准，立即把刚放下的方块恢复到虚拟代价层。
- 当前完整规划足迹向前达到 `0.48 m`，恢复方块后可能出现“机器人足迹已经覆盖致死栅格”，导致下一任务从碰撞起点启动，Nav2 单次内部恢复可达 22 次。
- 已采用的修复：刚放下的方块仍保留在 `/scan_safety` 中用于硬防撞，但暂不加入虚拟代价层；机器人离开到中心距 `0.70 m` 后再恢复。
- QoS 可靠性修复：不依赖短暂的 `TASK_COMPLETED` 单帧状态，改为每帧扫描持久化 `tasks[]` 列表，并以 `(任务序号, 方块ID)` 去重。
- 新发现的恢复失效根因：Gazebo 中底盘实体名为 `six_arm`，节点旧默认值却是 `originbot`，导致节点一直取不到机器人真值坐标，`0.70 m` 离开放置点后的恢复条件永远无法成立。默认模型名已改为 `six_arm`，运行参数实测一致。
- 状态：已编译并加载；等待完整运行验证 `Holding ... out` 与 `Restored placed cube ...` 两条事件。

### 4. 第三个物块长期无速度输出

- 日志证据：`/cmd_vel_nav_raw` 有非零角速度，而 `/cmd_vel_smoothed` 为零，最终 `/cmd_vel` 无输出。
- 已确认根因：SIPP 在 `WAIT_AT_STOP_LINE` 与 `PREPARE_TO_PASS` 之间振荡；旧逻辑要求“先有被门控前的前进速度才能 PASS”，但未 PASS 时又不允许前进，形成循环依赖。
- 已采用的修复：取消该循环依赖，同时保留固定出发航向、安全时间窗、最新 MPPI 接受结果和安全轨迹比例不低于 80% 等约束。
- 验证：修复后曾从 `PREPARE_TO_PASS` 正常进入 `PASS_COMMITTED`，约 32 秒推进 `1.596 m`。

## 二、参考工程对比结论

### `mppi_lstm_critic`

可借鉴点：按预测时间对齐机器人采样轨迹与动态障碍轨迹；区分硬碰撞和软风险；结合离开动态障碍轨迹通道的时间与相对运动方向评分。

不整包替换原因：当前版本已进一步包含预测时间戳过期、轨迹插值、SIPP 状态软代价、接近/远离方向权重、安全轨迹比例反馈、初始危险状态逃逸处理和预测末端处理，整体比参考版完整。替换会造成能力回退。

### `yzbot`

可借鉴点：

- 动态风险判断与最终速度门控分层；
- WAIT 状态带最短保持时间，避免频繁抖动；
- 恢复行为必须改变策略，而不是无限重发同一目标；
- 任务、导航、机械臂状态持续发布，方便可视化和复盘。

当前工程的 SIPP 速度门已覆盖参考 `behavior_manager_node.py` 的大部分功能，因此不再叠加第二个 `/cmd_vel` 门控节点，避免多发布者相互抢占。

### `auto_move_obstacle`

可借鉴点：移动障碍严格沿已知起终点往返、低速运行、到端点后平滑换向，物理参数限制碰撞冲量。

当前 world 已采用低质量、低摩擦、无弹跳、较低接触速度和有限驱动力，移动路线与预测配置保持一致；重点继续核对实体路线、静态地图与预测路线三者一致性。

## 五、Gazebo 与 CoStudio 稳定性根治

### 1. “界面还在/服务 active，但没有仿真数据”

- 旧架构使用组合 `gazebo` 启动器；VMware 的 OpenGL/SVGA 上下文偶发使 `gzclient` 以 clean exit 退出，组合启动器随即把 `gzserver` 一并结束。
- systemd 旧配置为 `Restart=on-failure`，clean exit 不会重启，于是出现服务看似正常、实际没有 `/clock`、激光和相机的假在线状态。
- 已改为独立启动 `gzserver` 与 `gzclient`：只有物理后端 `gzserver` 退出才关闭整套 launch；`gzclient` 单独 `respawn=True`，3 秒后自动重建；systemd 改为 `Restart=always`。
- 实测：人工结束旧 `gzclient` PID 61805 后，新 PID 65651 自动生成，而 `gzserver` PID 61803 保持不变，任务物理状态不会因显示端崩溃而丢失。

### 2. Windows CoStudio 无画面

- 本次直接原因是 Windows 本地没有监听 `localhost:9090`，而不是 ROS 相机停止发布。
- 已重新建立 `localhost:9090 -> u22:127.0.0.1:9090` 的 SSH 长连接，并确认 TCP 连接成功；CoStudio 已重新启动。
- 当前数据链：相机约 `4.5 Hz`，`/scan_safety` 约 `19.5 Hz`，`rosbridge_websocket` 与 `rosapi` 节点均在线。
