# 参考代码吸收与一键启动说明

## 2. 已吸收的优秀设计

### 2.1 MPPI 动态障碍评价

参考 `mppi_lstm_critic` 的时间序列逐点风险、危险区硬惩罚和尽早离开风险区思路，当前版本已实现：

- 对机器人轨迹与障碍预测轨迹按时间对齐，不只看静态最近距离；
- 使用相对接近速度和 TTC 区分“正在靠近”与“已经远离”；
- 对仍停留在预测占用管内的轨迹施加提前退出代价；
- 对远离障碍的轨迹折减软代价，但任何状态下都保留硬碰撞否决；
- 预测数据陈旧或长度不足时执行保守插值/降级，不使用过期结果冒险通过；
- MPPI 将可行率反馈给上层 SIPP，SIPP 决定等待/通过时机，MPPI 负责连续局部避让。

### 2.2 预测器与端点反射

参考 `yzbot/lstm_predictor_node.py` 的历史窗口、归一化、模型时间步一致性和往返端点约束，当前版本已实现：

- 使用近期运动方向与中位速度抑制单帧噪声；
- 检测长时间观测中断后重建历史，避免旧轨迹污染；
- 预测越过巡逻端点时按真实往返路线反射；
- 模型不可用或历史不足时使用受边界约束的运动学预测，而不是输出无效轨迹；
- 两个移动障碍的预测及风险管通过 MarkerArray 发布给 CoStudio。

### 2.3 移动障碍物世界插件

参考 `auto_move_obstacle.cc` 的可配置起终点、自动换向和周期状态输出，当前插件进一步改为：

- 严格按真实物理步长积分，不使用固定 `dt`；
- 到端点前平滑减速并准确换向；
- 使用速度/力学方式驱动实体，保留真实碰撞关系；
- 巡逻线分别使用 `(-2, 2.8)↔(1, 2.8)` 与 `(5, -3)↔(5, 0)`；
- 不采用参考代码的 `SetWorldPose` 瞬移方案，防止接触时把小车弹出地图。

### 2.4 任务状态机、恢复和数据观测

参考 `behavior_manager_node.py`、`mission_controller.py`、`system_status_node.py` 和 `data_logger_node.py`，当前版本已实现：

- 完整的请求题目、语言解析、导航取件、精确靠泊、抓取、搬运、放置和恢复状态；
- 等待/通过带确认与释放滞回，防止临界距离反复切换；
- 导航失败时先停车、取消旧目标、清理局部/全局代价地图，再按当前任务进度重规划；
- 导航看门狗同时检查路径剩余量和底盘真实位移，合法绕行不会被误判为卡死；
- 新增 `/system/status`（JSON）和 `/system/status_text`（看板文字）2 Hz 状态汇总；
- 运行快照写入 `/home/ros/dev_ws/logs/runtime_status_*.jsonl`，不记录大体积图像消息；
- 正式运行中发现并修复了“放置完成回调重入导致任务索引连跳”的竞态，任务完成现在只能提交一次。

### 2.5 真实近距离抓取

参考 `auto_grasp_moveit.py` 的预抓取、夹爪闭合和抓取阶段化思路，当前实现采用更适合本车模型的动态 IK：

- 先到已验证的物块预靠近点，再由保持碰撞监控的精确靠泊进入抓取工位；
- 只有物块进入两指中心的严格三维窗口后才允许闭合，不支持远距吸附；
- 动态 IK 将目标送到夹爪中心，实测抓取位置误差约 0.8 mm；
- 抓取后由 Gazebo 物理循环内的刚性携带插件驱动物块，避免 ROS 高频服务造成悬浮、竖直抖动或回执丢失；
- 放置后先等待真值稳定，并要求物块中心与完整机械臂足迹保持 0.92 m 安全净距，才把该物块恢复为规划障碍。

### 2.6 连续五物块投放与区域边界

本次针对“第 1 块已放好后，第 2 块在同一区域入口被虚拟障碍层卡住”和“方块中心在 A/B/C 内、边缘却越出标线”两个问题，增加了以下闭环：

- 按 Gazebo 世界真值纠正 A/B/C 区域坐标；旧布局中的 A 区坐标不再参与排障判断；
- 为每个区域配置 5 个彼此分离、完整位于 1.0 m × 0.5 m 区域内的槽位；
- 放置前从 Gazebo 读取其他已归位物块，选择首个空闲且运动学可达的槽位；
- 使用同一套已用于近距离抓取的 FK/IK，把夹爪实际送到选定槽位上方，再张爪让物块自然下落；
- 放置后以区域坐标系检查“完整物块”边界，而不是只判断底盘接近区域；若极少数接触冲量把 3 cm 方块滚过边线，才执行一次受限的安全回位并记录警告；
- 仅在“正在向同一投放区的最终靠泊”阶段临时放行该区内已经归位的方块的虚拟膨胀层；普通运输、取件和其他区域路径仍把全部方块视为实体障碍。

已在正式任务第 1 件实测：`red_cube_1` 选择 `zone_a` 第 1 槽位，IK 残差 1.5 mm，完成物理下落后通过“完整在 A 区内”真值检查；安全离场后自动开始第 2 件，无入口死锁。

### 2.6 识别和可视化

- 识别结果只保留置信度不低于 0.80 的目标；
- 原始摄像头与标注图使用同一时钟链路实时发布；
- 摄像头、标注图、地图、机器人轨迹、预测轨迹、动态风险管、任务状态及大模型解析结果均通过 Rosbridge 提供给 Windows CoStudio；
- Windows 端连接地址：`ws://localhost:9090`。

## 3. 明确未照搬的内容

- 未使用移动障碍物瞬移或固定时间步，因为这会产生不真实的碰撞冲量；
- 未使用远距离 LinkAttacher 式吸附，抓取必须通过靠泊和夹爪窗口真值检查；
- 未使用“机器人位于障碍路径上就放行”的绕过条件，物理硬碰撞始终有否决权；
- 未复制参考工程的地图坐标和模型阈值，所有坐标均以当前比赛 world 和实测可达点为准；
- 未把大图像写入状态日志，避免虚拟机 I/O 和内存压力。

## 4. 虚拟机一键启动

虚拟机登录图形桌面后，用户级 systemd 服务会自动启动整套系统，并打开 Gazebo 和实时日志终端。

核心文件：

- `/home/ros/dev_ws/scripts/run_competition.sh`：统一启动 ROS 2、Gazebo、导航、感知、机械臂、任务执行器和 Rosbridge；
- `/home/ros/dev_ws/scripts/competition_control.sh`：启动、停止、重启、查看日志和发布正式任务；
- `/home/ros/dev_ws/scripts/competition_live_dashboard.sh`：独立状态面板，持续显示服务状态、导航/抓取接口、Rosbridge 与任务 JSON；
- `/home/ros/dev_ws/scripts/wait_nav_ready.sh`：确认 `bt_navigator` 真正 ACTIVE；若首次登录高负载导致生命周期中断，则让 systemd 干净重启，而不是假报“已启动”；
- `/home/ros/.config/systemd/user/moon-warehouse.service`：登录自启服务；
- `/home/ros/.config/autostart/moon-warehouse-live.desktop`：登录后打开实时日志；
- `/home/ros/Desktop/比赛系统一键启动.desktop`；
- `/home/ros/Desktop/比赛系统停止.desktop`；
- `/home/ros/Desktop/发布正式任务.desktop`。

Windows 端还新增了 [一键启动比赛系统.cmd](/C:/Users/奶龙/Desktop/算法/一键启动比赛系统.cmd)：它会启动虚拟机比赛服务、建立 `localhost:9090 → u22:9090` 隧道并打开 CoStudio。CoStudio 数据源固定使用 `ws://localhost:9090`。

桌面操作：

1. 双击“比赛系统一键启动”启动或恢复全部软件；
2. 双击“发布正式任务”按比赛流程生成题目并执行；
3. 双击“比赛系统停止”安全停止整套 ROS/Gazebo 进程。

终端等价命令：

```bash
/home/ros/dev_ws/scripts/competition_control.sh start
/home/ros/dev_ws/scripts/competition_control.sh task
/home/ros/dev_ws/scripts/competition_control.sh logs
/home/ros/dev_ws/scripts/competition_control.sh restart
/home/ros/dev_ws/scripts/competition_control.sh stop
```
